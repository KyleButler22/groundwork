## Notes for whoever (or whichever agent) picks this up next

- Read `docs/*.md` before touching schema, intake, or either generator — they carry the reasoning, not just the shape, and several non-obvious decisions (goal asked last, variety floor of 2, the block sliding on missed sessions, isometrics needing their own metric type, `MealPlanEntry.servings` always meaning "eaten in this entry" even for a fresh dinner with a leftover) will look like bugs if you don't know why they're there.
- The Claude memory files `calisthenics-app*` and `calisthenics-recipe-corpus` (if you have access to them) carry the same context and a few things `docs/` doesn't — notably the recipe corpus sizing rationale.
- `npm run verify` before committing anything that touches `supabase/` or `src/generators/`.
- **Any new "generate a plan" write path must archive existing `status: 'active'` rows first.** `workoutPlans`/`mealPlans` are read back via `.where('status').equals('active').first()` with no other tiebreaker — a second active row for the same table makes that query's result arbitrary, not "the newest." `intake.ts`'s submit() and `mealPlan.ts`'s `generateFreshPlan()` both do this immediately before their `.add()`; copy that pattern rather than adding a bare `.add()` anywhere else.
- **Any write to Dexie that passes through a value which came from a reactive Pinia ref needs `toRaw()` — this has now bitten three separate times, in three different shapes.** A Vue reactivity Proxy anywhere inside an object passed to `db.<table>.put()`/`bulkPut()`/`bulkAdd()` throws `DataCloneError` at the IndexedDB layer; TypeScript and Dexie's types both accept it silently, so it only ever shows up by actually exercising the write in a browser.
  1. `mealPlan.ts`'s `toggleLock`/`toggleGroceryItemChecked` — an array FIELD (`GroceryItem.sourceEntryIds`) on a row read straight out of a reactive ref.
  2. `plan.ts`'s `toggleItemChecked` (this session) — subtler: `applyWorkoutLog`'s return value passes every pattern it DIDN'T touch straight through from whatever `levels` array was passed in, unchanged. Passing `levels.value` directly meant those untouched entries were still live Proxies sitting in the same array as freshly-computed plain objects for the touched ones — `bulkPut` throws on the first Proxy and Dexie never attempts anything after it in that call, so only some prefix of the array actually persisted, silently. Fixed with `levels.value.map((l) => toRaw(l))` at the call site, not a spread — the risk isn't "this one row", it's "any element of an array read from a ref, including ones a function only echoes back unmodified."
  3. Watch for a FOURTH shape: a value returned by a pure function that only PARTLY rebuilds its input (spreads some entries, passes others through by reference) is exactly the pattern that hides this, because it looks fine in every test (pure functions get plain-object test fixtures, never real Pinia refs) and only breaks against live reactive state.

  General rule going forward: `toRaw()` at the point a reactive-ref-derived value is ABOUT to be written, not at the point it's read — and if that value is an array, map `toRaw()` over every element, not just the array itself (`toRaw()` only strips the outermost proxy layer). Don't trust a stale browser tab's console history when chasing this class of bug either — it accumulates across navigations in this environment's tooling, which has twice now briefly looked like a fix hadn't worked when it had, or like a bug was present when it was actually a stale log; a fresh tab (or a direct IndexedDB read) settles it for certain.
- **Any new seed-file text column can contain a semicolon** (recipe instructions do, routinely — "Heat oil; soften onion..."). `parseInsertRows` (`src/generators/__fixtures__/sqlParse.ts` and `scripts/lib/sqlParse.mjs`) now scans for the statement-terminating `;` quote- and paren-depth-aware rather than the first literal `;`, specifically because of this — see the "recipe detail view" entry above for the bug it caused (78/200 recipes silently lost all their `recipe_steps` rows client-side). If you ever rewrite this function again, keep it string-aware; a plain regex/`indexOf` for `;` will reintroduce the same silent-truncation failure the moment some future column's text contains one.
- **A store action that does read-modify-write on a shared ref (read the array, compute the next one, reassign it) needs to join the SAME mutation queue as every other action touching that same ref — not its own separate queue.** `plan.ts` learned this twice: `toggleItemChecked` got the first queue defensively; `updateSetLog` needed one for real (reproduced, not a testing artifact — editing a set's reps and then its weight back to back silently dropped the first edit, the second call's stale read overwriting it). Both were routed through ONE shared `mutationQueue` because both read/write `setLogs.value`/`workoutLogs.value` and could race against EACH OTHER, not just against repeated calls to themselves. A new queue per function would only guard a function against itself.
- **Don't latch a "stable, once-per-visit" value onto the first non-null result of a computed that depends on data loaded by several separate async assignments.** `DashboardView.vue`'s fix for "Today" losing a session's checkmarks (see above) first tried latching `displayedSessionId` onto `nextSession`'s first non-null value — but `loadActivePlan()` (`plan.ts`) assigns `sessions.value` well before `workoutLogs.value` (a later, separate `Promise.all`), so there's a real reactive tick where sessions are loaded but nothing shows as completed yet, and `nextSession` computed THEN is wrong. The fix latches on `loading` going `false` instead, which only happens after every assignment in `loadActivePlan()` has landed. The general shape to watch for: a `computed` that reads from more than one ref populated by the same async function is only trustworthy once that function's `loading` flag says it's actually done — not the moment any one dependency first looks non-empty.
- **Any content table using a `gen_random_uuid()` primary key in Postgres cannot have its local-file-seeded id trusted as stable once real Supabase sync exists.** `Ingredient`/`Recipe` use their own slug as `id` when parsed from the local seed file (no way to predict a real uuid client-side) — real content sync replaces them with server-assigned uuids that have zero relationship to the slug. Every local row referencing one of these ids (meal plan entries, grocery items, feedback, pantry, disliked ingredients) needs remapping through the one thing both sides share — the slug — the moment real content ever replaces local-file content for an existing install; `claimLocalData.ts` does this once, for the one real trigger point (first sign-in). Integer-keyed content (movement library) does NOT have this problem — the local parser and Postgres's `serial` sequence both assign ids by strict file-order insertion, so they coincidentally but reliably agree on a freshly-seeded project. If a NEW uuid-keyed content table is ever added, assume it needs the same remap treatment, not the movement-library kind.
- **A generic camelCase↔snake_case row mapper beats hand-writing one function per table once the table count is large enough — but test the digit-after-underscore case.** `sync.ts`'s `toRow`/`fromRow` replaced an originally-planned "~40 hand-written mappers" approach once the actual table count made that clearly worse. The one regex gotcha: `/_([a-z])/g` misses `ingredients.kcal_per_100g` (`_1` isn't `_[a-z]`) — needs `[a-z0-9]` in the character class. `.toUpperCase()` on a digit is a harmless no-op, so the same replacer function still works once the class is widened. Caught by a unit test before it ever reached a real pull, not by noticing a runtime bug.
